# Seamlet SDK

The rules of this project for agents and humans. The development process is set by Cyberzavod: stages, roles, and general principles come from its harness, and here is only what belongs to the project. The files for a specific agent (for example, `CLAUDE.md`) are created by `npx cyberzavod sync` on top of this file.

## About the project

What a site installs to be edited in the Seamlet CMS. The CMS (a separate, closed product) stores content, signs people in and publishes; this repository holds only what runs on a site, and it is public.

- TypeScript, strict (`astro/tsconfigs/strict` plus `noUncheckedIndexedAccess`, `noUnusedLocals`, `noUnusedParameters`). ESLint with `strictTypeChecked` and an exhaustive `switch` over a union; Prettier with `prettier-plugin-astro`; Vitest, with jsdom for the DOM (`// @vitest-environment jsdom`); tsup builds the package. Node 24+, npm workspaces.
- Everything is in English: code, comments, messages, tests, commits, documentation. Texts a site's visitor or the CMS's user reads are in Russian.
- Every Russian text a person reads (the interface, messages, pages, letters, documentation) follows `.claude/skills/russian-copy/SKILL.md`: information style, concrete facts and benefits instead of abstractions, no AI clichés («уникальный», «инновационный», «индивидуальный подход»), no bureaucratese and no empty promises. Read it before writing Russian text; the review checks every changed Russian line against it.

## Architecture

- `packages/astro` — `@seamlet/astro`, published to npm.
  - `src/schema` — the schema language, the one description of content: field kinds (`text`, `richText`, `number`, `date`, `time`, `image`, `file` (a PDF uploaded in the CMS), `link`, `url`, `toggle`, `choice`, `choices`, `slug`, `reference`, `references`, `group`, `collection`) and their builders, `ContentOf`, `defaultContent`, `parseContent` (brings any input to the shape of a schema, with issues by field path), `editable<Content>()` (the typed marker `data-cms-path` on the element that shows a field or a record) and `resolveFieldPath` (`field-paths.ts`, with `FIELD_PATH_SEPARATOR`, the one separator of a path written as text), the one rule of where a link may lead (`link-addresses.ts`: `linkTargetOf`, and `safeHref`, through which a site and the bridge put an address into markup, since a draft may hold any), what a value read from JSON is (`json-values.ts`), the attributes a site puts on what it hides and shows itself (`reveal-markers.ts`), on what moves (`popover-markers.ts`: `data-cms-popover`, a field edited in the editor's popover only) and on the texts its code owns (`fixed-text-markers.ts`: `data-cms-fixed`, which the checks of unmarked texts leave out). Formatted text (`rich-text.ts`) is data, never HTML: paragraphs and lists of pieces with `bold`, `italic` and `href` (checked by the rule of links), read in one normal form (empty pieces left out, neighbors with the same marks joined), its lines given by `linesOf`; a plain string is read as paragraphs, and `inline` keeps one paragraph. `components/RichText.astro` renders it with the site's own elements, and the bridge's `rich-text-dom.ts` with the same ones (a test renders both and compares them). A photo may carry a `focus` (0 to 1 from the left and the top), which `imagePosition` turns into `object-position`. `presets.ts` holds the sets of fields almost every site has (`seoFields`, `contactsFields`, `openingHoursField`, and `productFields`, the fields of a product of a catalog with its characteristics as pairs of a name and a value), plain groups and collections of the usual fields. Every record of a collection has an `id` (`record-ids.ts`): `parseContent` keeps a valid one and never makes one up, so it gives the same content for the same input; `withRecordIds` gives ids to records without one (the CMS does it when it loads and saves), and `newRecord` starts a record with one. References are checked against the whole content after the fields (`reference-checks.ts`): an id its collection does not have is kept with the issue `missing-record`. A collection may have a page for each of its records (`record-pages.ts`: `recordPages(schema, { collection, path: "/menu/[record]", shows })`, with a typed `pathOf` for links, `shows` leaving the pages of some records, hidden ones, off the site but not out of the preview, `recordPageAt` and `recordAt` reading an address back): the address of a record's page is its `slug` (a field of a record, one per record, `read-fields.ts` refuses it elsewhere as `misplaced-slug`), or its id while it has none; `slugs.ts` is the one rule of a slug (the letters of a page's address, `PAGE_SEGMENT`, `MAX_SLUG_LENGTH`) and spells one from Cyrillic words (`slugOf`), and `slug-checks.ts` checks a slug against the other records of its collection after the fields (`taken-slug`, another record's slug or id). The forms of a site's requests are plain data too (`request-forms.ts`: `requestForm` with `requestText`, `requestLongText`, `requestPhone`, `requestEmail`, `requestChoice`, read back by `readRequestForm`); `request-values.ts` checks what a visitor sends (`readRequestValues`, the request's own keys: its form, its page, the consent and a field only programs fill), the same in the browser and in the CMS, `request-events.ts` names the events the site's code hears of a form, `request-addresses.ts` where the requests go, and `privacy-policy.ts` the business's two documents a visitor's checkbox links to, pages of the site: the consent, a document of its own (`CONSENT_PAGE_PATH`, `privacyConsentFields`, `privacyConsentTextOf`), and the policy in the sections Роскомнадзор recommends (`PRIVACY_PAGE_PATH`, `privacyPolicyFields`, `privacyPolicyTextOf`): the business is the operator of its visitors' data and Seamlet only passes requests on. Plain data that survives JSON, pure TypeScript: sites render with it, and the CMS checks and stores content with the same code (`@seamlet/astro/schema`).
  - `src/bridge` — the bridge on a site's preview. `connectToEditor({ editorOrigin })` does nothing outside a frame, says `ready` with its `PROTOCOL_VERSION` and, once the editor connects with the schema, reports where the marked elements are, what a person does, types texts in place and renders the editor's drafts. `page-reveals.ts` opens what hides a field: a click on the summary of a `<details>` opens it, a click on a radio button or a checkbox (or its label) flips it, so tabs and filters made with CSS work, a part marked as moving holds still in the editor while the pointer is over it and once a field in it is chosen and is never typed in place (`held-motion.ts`), the field the editor scrolls to has every `<details>` and `data-cms-reveal` part around it opened, and what was opened or flipped is opened or flipped again in a page rendered anew (a part known by its id, or by the field marked on it, in it or around it). A click chooses the smallest marked element whose box holds its point, in the block around the one it landed on (`marker-picks.ts`, `pickedPathAt`, the one rule the editor applies too), and a text outside every marked element is reported as the site's own (`static-texts.ts`). Every box is reported with the part of it a person sees (`visible-boxes.ts`: cut by the ancestors that clip it and by the parts fixed over it across its width, a sticky header; `shown` of a marker, read by `seenBoxOf`), and clicks are chosen by that part; a field the page shows more than once is told by its `copy` on hover, and a typing goes into the copy a click made ready (`copyToType`). A number and a time are typed in place when their element shows the value alone, with spaces between thousands or a decimal comma (`typed-values.ts`). Typing in place, plain or formatted, shares one lifecycle (`typing-sessions.ts`: Escape ends it and keeps the text); `rich-text-layouts.ts` says how a formatted text stands in its element (paragraphs and lists, or one line), and `typed-selections.ts` reports its selection. A draft rendered while a text is typed or the page pressed is held and shown once that is over, unless a newer one comes. `event-listening.ts` is how the bridge holds listeners and lets go of them together. What the editor cannot reach is checked with pure code that runs in the browser and on a build alike: `unmarked-texts.ts` (`unmarkedTextsOf`, the visible texts of a page, read as plain nodes, in no marked element and none marked `data-cms-fixed`) and `covered-fields.ts` (`coveredFieldsOf`, the fields in view a click reaches at none of the points tried, asked of the browser through a hit test); `page-checks.ts` runs both on the preview in the editor's frame and writes them to its console, the texts once and each covered field once as it comes into view, telling the editor nothing. `messages.ts` is the one description of what the bridge and the editor say to each other with `postMessage`; each side reads what it gets into those types and drops the rest, and hears only the other's window and origin. `PROTOCOL_VERSION` is raised whenever a message changes in a way the other side cannot read: sites update the package when they like, so the editor meets bridges of other versions.
  - `components/RequestForm.astro` and `src/request-sending.ts` — a form of requests: plain elements posted to the CMS without a script, with a checkbox of consent of its own; its labels and consent are the code's (`data-cms-fixed`), and its button too unless `submitMarker` names the field its words come from; the script, loaded by `client.ts` only on a page with a form, checks what was typed, sends it in place (a request stopped on its way is posted as a plain form) and dispatches the events, the first of them cancelable, so the site's code sends a request its own way.
  - `src/feeds` — `@seamlet/astro/feeds`: the catalog written for the places that sell it, from the published content, plain text a site serves from its build: `yandexFeedOf` (YML), `avitoFeedOf` (Avito's autoload, the fields its category asks given by the site) and `productOffersOf`, the offers of `productFields` records (hidden ones and ones without a price left out); `xml.ts` escapes. ESLint keeps it to itself and the schema language. `src/schema/rates.ts` is a calculator's rates the owner keeps (`ratesField`) and the sum a visitor's choice comes to (`estimateOf`).
  - `src/search` — `@seamlet/astro/search`: what makes a site found by search engines and AI assistants, plain text and data made from content. `sitemapOf`, `robotsTxtOf` (one group naming `*` and `SEARCH_CRAWLERS`, so no crawler skips the closed parts) and `llmsTxtOf` write the files the integration serves; `localBusinessOf`, `businessContactsOf`, `openingHoursSpecificationOf`, `productOf`, `breadcrumbsOf` and `faqPageOf` build schema.org things from the presets, and `structuredDataText` writes them as JSON-LD with `<` escaped, which `components/StructuredData.astro` renders as a data block. ESLint keeps it to itself, the schema language and the feeds' `xml.ts` and `offers.ts`. The routes (`routes/sitemap.ts`, `robots.ts`, `llms.ts`) list the pages the site shows with `search-pages.ts` from the content published at that moment (`content-cache.ts`, half a minute); `search-files.ts` names the files and the parts closed to crawlers, and leaves a file to a site that serves its own.
  - `src/protocol.ts` — what the CMS's editor needs to speak to the bridge (`@seamlet/astro/protocol`): the messages, their readers and the rules both sides share. `@seamlet/astro/bridge` also gives `connectPage`, for the editor's tests.
  - `src/index.ts` — the integration `seamlet({ sitemap, robots, llms, checks })`: it reads the site's `seamlet.json` (`site-config-file.ts`; `CMS_ORIGIN` of the environment takes the place of its `cms`, for a build for another CMS) and gives the site's build virtual modules (`virtual:seamlet/config` with the site's id, its title and the CMS's origin, `virtual:seamlet/site`, the site's module `src/seamlet.ts`, `virtual:seamlet/search` with `site` of the Astro config and the sitemap's address), `/sitemap.xml` (only with `site`; the build warns without it), `/robots.txt` and `/llms.txt` unless the site has its own or turns them off, the preview (`/preview/[...page]`, `routes/preview.astro`, with `preview-requests.ts`: an address of no page answered at once, `isPageAddress`; `GET` with the published content, where a record the editor added since is blank at its id, `previewContentAt`, until the draft renders; `POST` with a JSON draft no bigger than 1 MB; `frame-ancestors` of the CMS, `noindex`, `no-store`) and the photos taken from the CMS (`/media/[site]/[file]`), both rendered on request (every answer of the preview, a refusal too, carries `previewHeadersOf`; the photos answer 502 when the CMS does not answer in time); after a build it copies the photos and documents uploaded for the site that the built pages refer to into the client output, a few at a time (`uploaded-photos.ts`), for a static host. Then it checks the texts of the pages (`checks`: `warn` by default, `strict` stops the build, `off`): `built-pages.ts` imports the built server of `@astrojs/node` without starting it, serves it on the loopback for a moment and renders every page of the description in the preview with the initial content (`checkedPagesOf` of `text-checks.ts`, the page of every record too), `html-page-nodes.ts` reads the HTML with parse5 into the nodes the check reads, and `unmarkedTextsReport` lists the texts, those of every page once; another adapter skips the check. `site-addresses.ts` names what every site has alike: `src/seamlet.ts`, `/preview`, `/media`. The bridge goes on every page as a tiny script (`client.ts`) that loads the bridge only on `/preview` in a frame: a script of the injected route would be left out of a static site's on-demand pages.
  - `seamlet.json` at a site's root (`SITE_CONFIG_FILE`, read by `readSiteConfig` of `src/schema/site-config.ts`): what is known of a site before it is built, its id in the CMS (`isSiteId`, the one rule of an id, which also names the host of its preview), its title and the origin of its CMS. The CMS reads the same file from the site's repository, so the id is written once.
  - `src/cli.ts` — the package's command (`bin`), `npx @seamlet/astro init` (`src/init`): writes `seamlet.json` and the smallest site module the CMS edits (`site-files.ts`: a schema with one text, `src/seamlet.ts`, a page component), each only where the site has none, and the module with its schema and page all or none (`write-site-files.ts`); a `seamlet.json` the site has names the site for the modules, otherwise the id comes from `--id` or the name in `package.json` (`siteIdOf`), and it prints what to do next (`astro add @seamlet/astro node`, a page that renders the content).
  - `src/site.ts` — `defineSeamletSite({ schema, initialContent, pages, recordPages, photos, forms })`, a site's one module, its id and title taken from `seamlet.json` (a page is its title for the editor, its component and where its search texts are; pages of records are a `recordPages(...)` with the component that renders a record, given `content`, `record` and `index`), with `pageOf` and `staticPaths` (`site-pages.ts`: what renders each page with a content, for one `[...page]` route; `previewPageOf` renders the pages the site does not show too, for the preview; `pageAt`, the site's own pages only, is deprecated), `loadPublishedContent` (the initial content while the CMS answers `unknown-site`, `published-answers.ts`, since a site connected from its repository is built before the CMS knows it; any other refusal, or no answer in 30 seconds, stops the build), `ownPhotoAt` (the image of the site's own photo at an address its content gives it, found by `photos`) and `description`, what the site tells the CMS about itself (`site-descriptions.ts`, checked as the CMS reads it, so a site the CMS would refuse stops its build with the reasons: with its pages of records, no page of its own among them and every record of the initial content with an address of its own), handed out at `/seamlet/site.json` (`SITE_DESCRIPTION_PATH`, `routes/site-description.ts`) and read by the CMS with `readSiteDescription` (`src/schema/site-description.ts`, with `readFields`, a schema read back from JSON; `checkSiteDescription` and `checkFields` give the reasons a description or a schema is refused): the CMS keeps no copy of a site's schema.
  - `src/own-photos.ts` — the one rule of the site's own photos (an address of the site that is not an upload of the CMS) and where the site hands them out for the CMS's editor (`/seamlet-photos/<address>`, `routes/own-photos.ts`, a redirect to the build's file of the photo); `@seamlet/astro/protocol` gives it to the CMS.
  - Its README is what a site's author reads.
- `examples/coffee-shop` — the test site, connected the way every site is: it takes `@seamlet/astro` from the workspace as an installed package, so it checks the package as a site uses it. Its `Dockerfile` builds it for a server.
- Tests: `*.test.ts` run in Node (jsdom when a file asks for it); `*.astro.test.ts` render Astro components, routes and a site's module with Astro's container, in a Vitest project of their package or example (`vitest.config.ts` there), the root `vitest.config.ts` running them all.

Boundaries, enforced by ESLint: `src/schema` imports nothing outside itself; `src/bridge` imports only `src/schema`; `src/search` only `src/schema` and the feeds' XML and offers; examples take only `@seamlet/astro`.

A site never renders content as raw HTML (`set:html`): the CMS's editor acts on what the preview says.

## Impersonal package

The package and this repository name no one: no site, client, business, person, server, host or domain, except the CMS's own `https://cms.seamlet.ru` as the default of `init` Seamlet (`seamlet.ru`) as the processor in the template of the privacy policy, which the law asks it to name, and Seamlet (`https://seamlet.ru/`) in the credit the README asks every site to carry in its footer. Examples, comments, tests, the README and the changelog use made-up names that point at nobody (`my-site`, `cafe`, «Моя кофейня», «ООО «Ромашка»», `example.ru`, `cms.example`) and never the sites built with Seamlet; the test site is a coffee shop with no name of its own. Nothing here depends on what runs elsewhere: a CMS is named by the version of the description it reads, never by its address or its releases. The review checks every change against this.

## Public API

- The package is public: a change of the schema language, of the messages or of what the integration adds is a change of its API, and it gets a version of the package (semver).
- A change of the messages the other side cannot read raises `PROTOCOL_VERSION`: sites update the package when they like, so the CMS's editor meets bridges of other versions.
- Commits follow Conventional Commits.

## Commands

- `make check` — the package's build, formatting check, types (`tsc` for the package, `astro check` for the examples), ESLint, Vitest, the examples' build. It must pass before a commit.
- `npm run dev:coffee-shop` — the test site on http://localhost:4322, its content from `CMS_ORIGIN` (`http://localhost:4321` by default).
- `npm pack --workspace @seamlet/astro` — what would be published. A release: raise `version` in `packages/astro/package.json`, merge, run «Publish @seamlet/astro» from the Actions tab (`.github/workflows/publish-astro.yml`: a version already on npm is refused, the published one is tagged `astro-v<version>`; npm trusts the workflow itself, run in the `npm` environment, with no token: trusted publishing).
